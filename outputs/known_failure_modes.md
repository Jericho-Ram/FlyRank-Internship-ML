# Known Failure Modes

Hand-maintained. Not generated by `scripts/04_evaluate_and_export.py`.
Each entry names a condition under which the score should not be trusted, and what was done about it.

## 1. Zero-impression pages cannot decline, and they carried the result

`3,388` of `30,000` rows in the bundled CSV (`11.3%`) have
`impressions_prev_30d == 0` and a declining rate of exactly `0.000` —
impressions cannot fall below zero. Scoring only the `26,612` pages where
decline was arithmetically possible, on one runtime:

| | Unfiltered | Filtered |
|---|---:|---:|
| Base rate | `0.542` | `0.611` |
| RF ROC AUC | `0.750` | `0.565` |
| RF Precision@50 | `0.740` | `0.600` |
| Hand rule ROC AUC | `0.627` | `0.380` |
| Hand rule Precision@50 | `0.240` | `0.460` |

Precision@50 of `0.600` against a base rate of `0.611` means the ranking has no
lift over random selection. The model was separating pages that could not
decline from pages that could — a filter, not a prediction.

**Fix.** Score only pages where decline is arithmetically possible. Pages with
no prior impressions go to a different question: is this page visible at all.

**Don't trust the score** on any unfiltered population, which includes every
number previously published from this repo.

## 2. The 90-day query window opens inside the label month

`fact_content_query_90d` has `window_start = 2026-04-02` and
`window_end = 2026-06-30`. A decision made on 1 April cannot use it.
Assumed, then measured in Test E of `w03_feature_leakage_check.ipynb`.

**Fix.** A guard that refuses to run if the feature window's end date falls on
or after the label window's start date. Assume nothing about a window; read it.

**Don't trust the score when** any feature table's window has not been read directly.

## 3. GA4 features are 59% missing, and missing for the wrong reason

At item grain, `sessions_mar`, `engagement_rate_mar`, `scroll_per_session_mar`
and `ai_share_mar` are absent because a client had no GA4 in March, not because
the page had no engagement. In the raw March slice only `413,966` of
`9,841,378` daily rows had GA4 available (`4.2%`), and the rest were zero-filled
rather than null — which would drag any engagement average toward zero silently.
Kept, with `ga4_usable` as a `0/1` flag and median imputation inside the fold.

**Fix.** Check per-fold feature importance before shipping.

**Don't trust the score when** importance sits on GA4 columns and clients differ
in GA4 coverage — the model is likely identifying clients, not measuring engagement.

## 4. The committed report did not reproduce

`outputs/model_report.md` published Precision@50 of `0.680`. A fresh clone on the
same data returns `0.740`. Two filtered runs in separate directories returned
identical figures, so the pipeline is deterministic — the committed report was
generated by an earlier state of the repo, or under different library versions.
Cause not confirmed.

**Fix.** Regenerate the report from a clean clone before quoting any figure from
it, and record the runtime. A number that cannot be reproduced from the public
repo is worse than no number.

## 5. The label is defined differently in the two slices

The bundled CSV's `trend_direction` is built from impressions:
`impressions_prev_30d == 0` gives a declining rate of exactly `0.000`, while
`clicks_prev_30d == 0` gives `0.517`, near the base rate. The warehouse label is
built from clicks — warehouse Test D found `61.1%` of rows with `clicks_mar == 0`
at a declining rate of `0.000`.

**Fix.** Label every figure with its slice. Same failure mechanism, different
column, different population size.

**Don't trust** any comparison that moves a number between the two slices.

## 6. Precision@50 is the most fragile metric in the table

It reads only the top 50 rows, so it moves first when tie-breaking changes.
ROC AUC held at `0.750` against a committed `0.747` across the same runs where
Precision@50 moved `0.680` to `0.740`.

**Fix.** Quote ROC AUC alongside Precision@50, never Precision@50 alone.
